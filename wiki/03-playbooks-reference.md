## 1. DEPLOY — Application Deployment

**Goal:** Release an application to the target environment.

**Required info:** App name, target environment (DEV / UAT / STAG / PROD), image tag or commit SHA.

### Pre-deploy Sub-steps (detect and execute before deploying)

Scan the ticket description for these signals — if present, execute them **before** the image deploy:

| Signal | Action |
|---|---|
| `Config/Secret update` section | Update AWS Secrets Manager first |
| `<sent via email>` / `<SRE-To be updated>` | ⚠️ Secret pending — **do not deploy until received** |
| `ENV:` section | Update Helm values or Secrets Manager |
| `SQL:` section with GitHub URL or inline SQL | Fetch, review, and run SQL migration (check order: before or after deploy) |
| `S3 Migration:` / `s3://` sync | Run `aws s3 sync` |
| `clean the cache` / CDN cache | Invalidate CloudFront distribution |
| `Backup` tables | Take RDS snapshot first |

### SQL Script Review

When a ticket contains SQL, the assistant automatically reviews each script before generating the guide:

| Severity | What Is Checked |
|---|---|
| 🔴 **Data loss** | `DELETE FROM {table}` without `WHERE`, `DROP TABLE`, `TRUNCATE`, `DROP COLUMN` |
| 🔴 **Breaking schema** | `RENAME COLUMN` — app may still reference the old name |
| 🟠 **Table lock** | `ALTER TABLE` adding `NOT NULL` column without `DEFAULT` on a large table |
| 🟠 **Type change risk** | `MODIFY COLUMN` / `ALTER COLUMN TYPE` — implicit cast may fail |
| 🟠 **No transaction** | Script not wrapped in `START TRANSACTION ... COMMIT` |
| 🟡 **Large write** | Mass `INSERT/UPDATE/DELETE` without batching on a large table |

If 🔴 or 🟠 risks are found: a Jira comment is posted before the guide is created, requesting developer confirmation. If no rollback plan is found: a separate Jira comment is posted with a suggested rollback template.

### Ordered Guide

```bash
# Pre-flight: verify image exists
aws ecr describe-images \
  --repository-name {ecr-repo-name} \
  --image-ids imageTag={tag} \
  --region ap-northeast-1

# Check current app status
argocd app get {app-name}-{env}

# S3 sync (if needed)
aws s3 sync s3://{source}/{path}/ s3://{dest}/{path}/ --region ap-northeast-1

# RDS backup + SQL migration (if needed)
aws rds create-db-snapshot \
  --db-instance-identifier {rds-instance} \
  --db-snapshot-identifier {app}-pre-{version}-$(date +%Y%m%d)
# Then run SQL migration after reviewing the script

# CloudFront cache invalidation (if needed)
aws cloudfront create-invalidation \
  --distribution-id {DISTRIBUTION_ID} \
  --paths "/*"

# Deploy (staging/prod = manual ArgoCD sync)
argocd app sync {app-name}-{env}
argocd app wait {app-name}-{env} --health --timeout 180
kubectl get pods -n {namespace} -l app={app-name}

# Rollback (if needed)
argocd app rollback {app-name}-{env}
# or revert image tag commit in k8s-manifest and re-sync
```

### Outcome Checklist

- [ ] SQL scripts reviewed (risks flagged on Jira if found)
- [ ] Pre-deploy sub-steps completed (secrets / S3 / SQL / cache as applicable)
- [ ] Image confirmed in ECR
- [ ] ArgoCD sync completed without errors
- [ ] All pods Running/Ready
- [ ] Smoke test passed on target URL
- [ ] No error spike at `{GRAFANA_URL}`

## 2. INFRA_CHANGE — Infrastructure Changes

**Goal:** Guide infrastructure changes that don't involve a code deploy — scaling, ENV updates, S3 CORS/IAM, nginx config, Terraform changes.

**Required info:** App/service name, target environment, specific change description (what the new value should be).

### Scale Pods

```bash
# Permanent: update in Helm values and commit
# Edit: helm/apps/{app-name}/values-{env}.yaml → replicaCount: {n}
# Commit → ArgoCD auto-syncs (dev/uat) or manual sync (stag/prod)

# Temporary (dev/uat only — reverted by ArgoCD on next sync):
kubectl scale deployment {app-name} --replicas={n} -n {namespace}
```

### Update ENV Variables

The location of ENV vars depends on whether the app is **frontend** or **backend**:

| App Type | Signal | Where ENVs Live |
|---|---|---|
| Frontend / CMS | Prefix `VITE_APP_*`, `NEXT_PUBLIC_*`, or repo is `cms-*` | GitHub Actions Secrets & Variables |
| Backend | Repo is `*-backend`, `*-agent`, runs on EKS | AWS Secrets Manager + ESO |

**Frontend apps (GitHub Actions):**
1. Go to `https://github.com/{your-github-org}/{repo}/settings/variables/actions`
2. **Variables** tab for non-sensitive values; **Secrets** tab for sensitive values
3. Re-trigger a deploy so the build picks up the new values

**Backend apps (Secrets Manager):**
```bash
# Get current values first (important — put-secret-value replaces the entire secret)
aws secretsmanager get-secret-value \
  --secret-id eks-{cluster-prefix}-{app-name} \
  --region ap-northeast-1 \
  --query SecretString --output text

# Update — include ALL existing keys plus the new/updated one
aws secretsmanager put-secret-value \
  --secret-id eks-{cluster-prefix}-{app-name} \
  --secret-string '{"EXISTING_KEY": "val", "NEW_KEY": "new-val"}' \
  --region ap-northeast-1

# Force ESO resync + restart the app
kubectl annotate externalsecret {app-name} \
  force-sync=$(date +%s) --overwrite -n {namespace}
kubectl rollout restart deployment/{app-name} -n {namespace}
```

### S3 CORS

Edit the relevant `s3-*.tf` file in `github.com/{your-github-org}/terraform`:

```hcl
cors_rule {
  allowed_headers = ["*"]
  allowed_methods = ["GET", "PUT", "POST", "HEAD"]
  allowed_origins = ["https://your-origin.com"]
  expose_headers  = ["ETag", "Location"]
  max_age_seconds = 3000
}
```

```bash
terraform plan -target=module.{bucket-name}
terraform apply -target=module.{bucket-name}
```

### S3 IAM Permission

Add the IAM ARN to `white_list_full_access_identifiers` in the relevant `s3-*.tf`:

```hcl
white_list_full_access_identifiers = [
  aws_iam_user.{service}-{env}.arn,
  "arn:aws:iam::{AWS_ACCOUNT_ID}:user/{new-user}",  # add
]
```

```bash
terraform plan -target=module.{bucket-name}
terraform apply -target=module.{bucket-name}
```

### Nginx / Ingress Config (upload limit, timeout)

Add annotations to the app's ingress in `helm/ingress-nginx/{env}/`:

```yaml
nginx.ingress.kubernetes.io/proxy-body-size: "50m"
nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-connect-timeout: "60"
```

```bash
cd helm/ingress-nginx/{env}
helmfile diff .
helmfile apply .
```

### General Terraform Change

```bash
terraform fmt && terraform validate
terraform plan -target={resource_type}.{resource_name}
terraform apply -target={resource_type}.{resource_name}
```

> ⚠️ Always use `-target` for scoped changes. Flag any destructive resource changes before applying.

## 3. SECRET — Secrets Management

**Goal:** Create or update a secret in AWS Secrets Manager.

> If the ticket is a DEPLOY that includes secret values — handle secrets as a sub-step inside the DEPLOY playbook, not as a standalone SECRET ticket.

**Required info:** App name, target environment, secret key name(s), new value(s) — or confirmation that values were sent via email.

### Secret Naming Convention

| Environment | Prefix | Example |
|---|---|---|
| Production | `{SECRET_PREFIX_PROD}` | `{SECRET_PREFIX_PROD}cc-backend` |
| Staging | `{SECRET_PREFIX_STAGING}` | `{SECRET_PREFIX_STAGING}cc-backend` |
| UAT / Dev | `{SECRET_PREFIX_UAT}` | `{SECRET_PREFIX_UAT}cc-backend` |

> Always read the exact secret name from `additionalManifests[0].spec.data[0].remoteRef.key` in the app's `values-{env}.yaml` — do not guess from the pattern alone.

### Update an Existing Secret

```bash
# 1. Get current values (required — put-secret-value replaces the entire secret)
aws secretsmanager get-secret-value \
  --secret-id eks-{cluster-prefix}-{app-name} \
  --region ap-northeast-1 \
  --query SecretString --output text

# 2. Update (include ALL existing keys)
aws secretsmanager put-secret-value \
  --secret-id eks-{cluster-prefix}-{app-name} \
  --secret-string '{"EXISTING_KEY": "val", "UPDATED_KEY": "new-val"}' \
  --region ap-northeast-1

# 3. Force ESO resync
kubectl annotate externalsecret {app-name} \
  force-sync=$(date +%s) --overwrite -n {namespace}

# 4. Restart the app
kubectl rollout restart deployment/{app-name} -n {namespace}
```

Alternatively, via AWS Console: Secrets Manager → `ap-northeast-1` → search → Retrieve → Edit → Save.

### Create a New Secret

```bash
aws secretsmanager create-secret \
  --name eks-{cluster-prefix}-{app-name} \
  --description "Secrets for {app-name} on {env}" \
  --secret-string '{"KEY_1": "value1", "KEY_2": "value2"}' \
  --region ap-northeast-1
```

Then add an `ExternalSecret` manifest to the app's Helm chart (`additionalManifests:` section):

```yaml
additionalManifests:
  - apiVersion: external-secrets.io/v1
    kind: ExternalSecret
    metadata:
      name: {app-name}
    spec:
      refreshInterval: 1h
      secretStoreRef:
        name: ai-aws-vault
        kind: ClusterSecretStore
      target:
        name: {app-name}
        creationPolicy: Owner
      data:
        - secretKey: KEY_1
          remoteRef:
            key: eks-{cluster-prefix}-{app-name}
            property: KEY_1
```

**When adding new keys** (not just updating values): update the `ExternalSecret` `data` section in `helm/apps/{app}/values-{env}.yaml` and commit. ArgoCD auto-sync + ESO will pull the new keys automatically — no manual ESO resync needed.

## 4. DNS — DNS Record Changes

**Goal:** Add or modify DNS records. For Zero Trust access, see Section 5.

**Required info:** Domain/subdomain, record type (A / CNAME / etc.), target value, environment.

### Which Repo to Edit

| Domain | Terraform Repo |
|---|---|
| `{your-org}.com` | `github.com/{your-github-org}/route53-{your-org}-com-tf` (files: `records_dev.tf`, `records_uat.tf`, `records_staging.tf`, `records_prod.tf`) |
| `{yourcompany}.ai` | `github.com/{your-github-org}/route53-{yourcompany}-ai-tf` |
| Zero Trust / VPN | `github.com/{your-github-org}/cloudflare-zero-trust-tf` |

> **Never edit DNS manually in the Cloudflare dashboard** — Terraform will overwrite any manual changes.

### Cloudflare CNAME Example

```hcl
resource "cloudflare_record" "{name}" {
  zone_id = cloudflare_zone.{zone}.id
  name    = "{subdomain}"
  value   = "{target}"
  type    = "CNAME"
  ttl     = var.ttl_app_endpoint
  proxied = false
}
```

### Route 53 CNAME Example

```hcl
resource "aws_route53_record" "{name}" {
  zone_id = aws_route53_zone.{zone}.zone_id
  name    = "{subdomain}.{domain}"
  type    = "CNAME"
  ttl     = 60
  records = ["{target}"]
}
```

### Apply Changes

```bash
terraform fmt && terraform validate
terraform plan
terraform apply
```

## 5. ACCOUNT_MGMT — Access Requests

**Goal:** Handle access requests — GitHub, Cloudflare Zero Trust, internal tools, AI accounts.

**Required info:** Full name/email of the user, system(s) to grant access, role/permission level, approver.

### GitHub Repository Access

```
github.com/{your-github-org}/{repo} → Settings → Collaborators and teams
→ Add GitHub username with role (Read / Write / Maintain)
→ User receives email invite
```

### Create a New GitHub Repository

```
github.com/{your-github-org} → New repository → Private
→ Set name, initialize with README
→ Add requested members with specified roles
```

### Cloudflare Zero Trust

```
Cloudflare Zero Trust dashboard → Access → Groups
→ Add user email to appropriate access group
→ User accesses via {ZERO_TRUST_URL}
```

IaC-managed policies: `github.com/{your-github-org}/cloudflare-zero-trust-tf`

### Metabase Access

```
{METABASE_URL} → Admin → People → Invite user
→ Assign to appropriate Group with correct DB permissions
```

### AI Tool Accounts (Claude, ChatGPT, etc.)

```
Log in to the team/org account for the relevant tool
→ Invite user's -company.com email
→ Assign appropriate seat/role per ticket
→ Notify user via Slack or email
```

### Outcome Checklist

- [ ] Access granted in relevant system
- [ ] User notified
- [ ] Approver confirmed in Jira

## 6. OFFBOARDING — Employee Offboarding

**Goal:** Remove all access for a departing employee.

**Required info:** Full name/email, official last day, list of systems to revoke access from.

### Standard Checklist

Apply items mentioned in the ticket:

- [ ] Gmail / Google Workspace — disable account, transfer Drive data to specified person
- [ ] Slack — deactivate account
- [ ] Claude / ChatGPT — remove from org
- [ ] VPN (Cloudflare Zero Trust + OpenVPN) — remove from access groups
- [ ] GitHub (`{your-org}` org) — remove member
- [ ] Jira & Confluence — deactivate Atlassian account
- [ ] AWS SSO — remove from AWS Identity Center
- [ ] AWS Active Directory — remove if applicable
- [ ] Metabase — deactivate user account

> ⚠️ **Revoke email last** — it's needed for password resets during the offboarding process.

## 7. NEW_RESOURCE — New Resources

**Goal:** Provision new infrastructure or onboard a new application.

**Required info:** Resource name, target environment, team/service owner. For databases: DB name, engine (MySQL/PostgreSQL), app user name. For Redis: service name, target env.

### New Database (MySQL or PostgreSQL)

> ⚠️ **Databases are created via SQL command in an existing RDS instance, not Terraform.** Only provision a new RDS instance if the ticket explicitly says "create new DB instance" / "new RDS".

**MySQL** (connect as admin):

```sql
CREATE DATABASE {db_name};
CREATE USER '{app_name}'@'10.10.%.%' IDENTIFIED BY '{strong-password}';
GRANT ALL PRIVILEGES ON `{db_name}`.* TO `{app_name}`@`10.10.%.%`;
FLUSH PRIVILEGES;
-- For staging/prod, also grant awsdms_control:
GRANT ALL PRIVILEGES ON `awsdms_control`.* TO '{app_name}'@'10.%.%.%';
```

**PostgreSQL** (connect as postgres admin):

```sql
CREATE USER {app_name} WITH PASSWORD '{strong-password}';
CREATE ROLE {app_name}_role;
GRANT {app_name}_role TO {app_name};
CREATE DATABASE {app_name} OWNER {app_name}_role;
\c {app_name}
GRANT USAGE ON SCHEMA public TO {app_name}_role;
GRANT ALL ON ALL TABLES IN SCHEMA public TO {app_name}_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO {app_name}_role;
ALTER SCHEMA public OWNER TO {app_name}_role;
\q
```

After creating the DB: update the app's Secrets Manager entry with the new `DATABASE_URL`, then force ESO resync + restart.

### New Redis Instance

> Redis runs as Docker Compose on dedicated EC2 servers — **not ElastiCache**. One container per service.

| Environment | Server |
|---|---|
| dev/uat | `{REDIS_SERVER_DEV_UAT}` |
| staging | `{REDIS_SERVER_STAGING}` |
| prod | `{REDIS_SERVER_PROD}` |

Steps:
1. SSH into the target Redis server
2. Find the next free port: `grep -r "EXPOSED_PORT" /data/{env}/*/.env | sort -t= -k2 -n | tail -3`
3. Create `/data/{env}/{env}-{service-name}/` with `data/` and `config/` subdirs
4. Write `.env`: `REDIS_PASSWORD={strong-password}` + `EXPOSED_PORT={next-port}`
5. Copy `sre-triage/configs/compose/redis.yml` and start: `docker compose -f redis.yml up -d`
6. Check if the new port is within the current security group range — if it exceeds `to_port`, update `aws_security_group.redis-server-{env}` in `sg.tf` and `terraform apply`
7. Add to app config: `REDIS_HOST`/`REDIS_PORT` → Helm values; `REDIS_PASSWORD` → Secrets Manager + ESO resync

### New Application

Generate:
- Helm chart: `helm/apps/{app}/`
- ArgoCD Application manifest: `argocd/overlays/{env}/apps/{app}.yaml`
- GitHub Actions workflows (prepare → build-and-push → deploy using `{your-org}/action-docker-build@v1` + `{your-org}/argo-deployer@v2`)
- ExternalSecret manifest (if the app needs secrets)

Register with ArgoCD (one-time):

```bash
kubectl apply -k argocd/overlays/{env}
```

### New S3 Bucket

```hcl
resource "aws_iam_user" "{service}-{env}" { name = "{service}-{env}" }

module "{service}-{env}" {
  source      = "./modules/s3-default-perm"
  bucket_name = "{service}-{env}"
  white_list_full_access_identifiers = [aws_iam_user.{service}-{env}.arn]
}
```

### New ECR Repository

```hcl
module "{service}" {
  source = "./modules/ecr"
  name   = "{service}"
}
```

### New Email / SES Identity

1. AWS Console → SES → Verified identities → Create identity → verify domain or email
2. Create SMTP credentials: IAM → new user → attach `SESFullAccess` → create access keys
3. Send credentials to requester via a **secure channel** (not Jira comments)

## 8. DEBUG / INCIDENT — Troubleshooting

**Goal:** Systematic diagnosis guide based on the reported symptom.

**Required info:** App/service name, environment, symptom description, time the issue started.

### Pod CrashLoopBackOff / App Down

```bash
kubectl get pods -n {namespace} -l app={app-name}
kubectl describe pod -n {namespace} {pod-name}
kubectl logs -n {namespace} {pod-name} --tail=100
kubectl logs -n {namespace} {pod-name} --previous --tail=100
argocd app get {app-name}-{env}
```

**Common causes:**
- Secret not found → check ExternalSecret and ESO sync status
- Wrong image tag → check ArgoCD app spec
- Resource limits → check Helm values `resources.limits`
- Dependency not ready (DB / RabbitMQ / Redis) → check service connectivity

### OOMKilled

```bash
kubectl top pod -n {namespace} -l app={app-name}
kubectl describe pod -n {namespace} {pod-name} | grep -A5 OOM
```

Fix: increase `resources.limits.memory` in `helm/apps/{app}/values-{env}.yaml`, commit and sync.

### HTTP 502 / 504

```bash
kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx \
  --tail=100 | grep {hostname}
kubectl get endpoints -n {namespace} {app-name}
kubectl describe service {app-name} -n {namespace}
```

### S3 403 AccessDenied

Check IAM policy — likely need to add the user ARN to `white_list_full_access_identifiers` in the relevant `s3-*.tf` (see Section 2 → S3 IAM Permission).

### Observability Links

| Tool | URL | Filter |
|---|---|---|
| Logs | `{LOGS_URL}` | `kubernetes.deployment.name: {app-name}` |
| Metrics | `{GRAFANA_URL}` | Select Prometheus data source for environment |
| Traces | `{TRACING_URL}` | Filter by service name + `APM_ENVIRONMENT` |

## 9. UNKNOWN — Unclassified Tickets

When a ticket cannot be confidently classified:

1. Summarize what was understood from the ticket
2. Ask 2–3 focused clarifying questions (env? app name? deploy or config change? urgent?)
3. Notify `#sre-team` on Slack with `Needs triage ⚠️` and the questions inline
4. **Do NOT create a Confluence page** until the ticket is classified

## 10. General Rules

These rules apply to all ticket types and all resolutions.

| Rule | Detail |
|---|---|
| **Never guess resource names** | Use patterns: secret `eks-{cluster-prefix}-{app}`, ECR `{ECR_PREFIX}{name}`, clusters `{your-cluster-prefix}-{env}-yazvvz` |
| **Secret pending = block deploy** | `<sent via email>` or `<SRE-To be updated>` means wait for the actual value before proceeding |
| **Prod always has a rollback step** | Every production change guide must include explicit rollback commands |
| **Destructive actions get a warning** | Prod deploy, SQL migration, deletion → ⚠️ flag + explicit confirmation note |
| **Never commit secrets** | `.env` files, raw secret values, SMTP credentials → never in any repository |
| **Partial info is OK** | Generate what you can, mark unknown fields as `{TBD — awaiting requester input}`, and post a Jira comment |
| **Namespaces** | `dev` = `{DEV_NAMESPACE}`, `uat` = `{UAT_NAMESPACE}` (both on `{uat-cluster-name}`); staging on `{staging-cluster-name}`; prod on `{prod-cluster-name}` |
| **`staging` = `stag`** | Used interchangeably across file names and resource names |
